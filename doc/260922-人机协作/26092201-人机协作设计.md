# 人机协作设计

传统总体设计、详细设计要写全评审材料。交给 AI 按原模版输出时，空章节会被写满，字段表、多套图、非功能清单叠在一起，人读不完，也看不清系统到底有什么。

这份文档把两份旧模版收成一种用法：**开工时人拍板，开发时 AI 按里程碑实现，文档只保留人能读完的契约和一张会更新的系统地图。** 可填写的空模版见 [26092202-设计模版.md](./26092202-设计模版.md)。

## 协作方式

| 阶段 | 人做什么 | AI 做什么 | 文档怎么变 |
| --- | --- | --- | --- |
| 开工 | 写契约：边界、里程碑、模块职责、已经拍板的决策 | 按契约复述理解，拆里程碑，人确认后再动手 | 契约冻结。改动要人确认 |
| 每个里程碑 | 看「本里程碑交付了什么」，按验收标准看结果 | 实现该切片，只改系统现状里变过的几行 | 增量记录，不重写全文 |
| 全程 | 用模块地图和主流程理解系统由什么组成 | 代码、接口定义、迁移脚本保存字段级细节 | 地图指向代码，不复制代码 |

篇幅：开工契约一个人约 10 分钟能读完。每个里程碑的增量不超过一屏。没有内容的可选章节直接删掉标题，避免模型把空表填满。

细节的权威来源：

- 接口字段：接口定义（OpenAPI、类型或路由注释）
- 表字段、索引：迁移脚本
- 配置项、缓存、容量数字：配置与对应里程碑的笔记

设计文档回答三件事：做什么、不做什么、系统现在由哪些模块和能力组成。

## 保留：开工契约

这些条目会改变实现方向。旧模版里的「功能描述 / 功能概述 / 设计思路 / 功能需求」合成下面 7 块，各写一次。

| 保留块 | 旧模版出处 | 写到什么程度 |
| --- | --- | --- |
| 要解决的问题 | 总体 1.1 系统概述；详细 1 功能描述 | 一段话。说清问题，不写文档自身的介绍 |
| 本期做 / 明确不做 | 两份模版都没有独立边界 | 「本期做」和「明确不做」各若干条，每条一行 |
| 里程碑与验收 | 两份模版都没有 | 3～7 个可独立交付的切片。每个切片写：交付物、人如何验收、依赖上一片什么 |
| 模块地图 | 总体 3.4.1 层次结构、3.4.2 功能需求和模块关系 | 模块名、一句话职责、不负责什么、依赖哪个模块。这是人理解「系统有啥」的主入口 |
| 核心场景 | 总体 3.3.1 系统用例图；详细 2.1 功能需求 | 3～7 条主路径：谁、在什么情况下、完成什么。工单只留编号和一句话 |
| 已拍板的决策 | 总体 3.2.1 关键算法和技术选型、3.2.2 核心数据结构 | 已经决定的选型、核心数据结构、为什么这样选。还没决定的不展开成长文 |
| 外部依赖 | 总体 2 依赖 | 依赖名称、类型、本系统用它的哪一项能力。一行一个 |

## 开发中维护：系统现状

这些让人在 AI 连续开发时仍能对上系统。只保留索引。每个里程碑结束时，改受影响的行。

| 保留块 | 旧模版出处 | 写到什么程度 |
| --- | --- | --- |
| 实体与关系 | 详细 3.3.1 表清单、3.3.2 ER 关系 | 实体名、为什么存在、关键业务字段、和谁有关系。全字段以迁移脚本为准 |
| 能力清单 | 详细 3.4.1 接口清单 | 名称、谁调用、做什么、同步还是异步。入参出参以接口定义为准 |
| 一条主流程 | 总体 3.3.2 系统流程图或 3.3.3 关键时序图，二选一；详细 3.2 设计图 | 只画本期主路径。时序图和流程图留一种 |
| 硬约束 | 详细 2.2 非功能需求；总体 3.5 里会改变结构的条目 | 只写会改变表结构、模块边界或接口形态的项。例如租户隔离、敏感字段、必须分库、必须幂等。每条写「约束」和「因此结构上必须怎样」 |

## 后置到代码或单个里程碑

这些内容在传统评审里要写全。在人和 AI 协作里会把文档撑厚，并和代码重复。某个里程碑真的需要时，在该里程碑记录里单开一小节。没有就不出现标题。

| 旧章节 | 放到哪里 |
| --- | --- |
| 详细 3.4.2 接口字段表 | 接口定义 |
| 详细 3.3 的全字段、索引、分表细则 | 迁移脚本。分库分表只在决定它的那个里程碑写结论 |
| 总体 3.4.3 配置；3.5.1 缓存；3.5.5 容量数字 | 配置文件，以及该里程碑的笔记 |
| 总体 3.5.2～3.5.7 安全、兼容、可移植、验证、部署的全套小节 | 本系统真有特殊要求时，收成硬约束里的几条 |
| 总体 1.2 文档概述、1.3 基线、第 4 章底稿链接 | 不进设计正文 |
| 总体 3.3.4 数据流程图；用例图、流程图、时序图同时画 | 主流程已覆盖的不再另画 |
| 详细 3.1 设计思路（与契约里的决策、模块职责重复的部分） | 已拍板的决策、模块地图 |
| 详细 3.5 其他 | 有具体事项时写入对应里程碑，不设常设杂项章 |

## 正文骨架

可填写版本见 [26092202-设计模版.md](./26092202-设计模版.md)。结构如下：

```markdown
# 系统名

## 1. 契约（开工时写，之后改动要人确认）
### 1.1 要解决的问题
### 1.2 本期做 / 明确不做
### 1.3 里程碑（交付物 + 人如何验收）
### 1.4 模块地图（职责 / 不负责 / 依赖）
### 1.5 核心场景
### 1.6 已拍板的决策
### 1.7 外部依赖

## 2. 系统现状（每个里程碑只改变过的行）
### 2.1 实体与关系
### 2.2 能力清单
### 2.3 主流程
### 2.4 硬约束

## 3. 里程碑记录
### M1 名称
- 交付了什么
- 相对契约的偏差（没有就写无）
- 现状里改了哪几行
```

人在初期参与的是边界和验收。阅读时看模块地图和主流程。AI 实现时，字段和配置留在代码里。文档只回答系统由什么组成、这一期交付了什么。
